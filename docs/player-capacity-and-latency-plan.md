# 自定义人数、自由开局与低延迟优化方案

日期：2026-11-16  
状态：主体改造已落地，并完成本机构建、自动测试、浏览器验证及 50/100/200 人短测；实测结果和未覆盖项见 [性能报告](performance-report.md)。下文“当前实现”表描述改造前的基线。

## 1. 目标与范围

本次改造围绕三个目标：

1. NPC 后台可自定义房间人数上限，玩家端同步显示，不再写死 50 人。
2. 队伍人数不均衡也可以开始；保留人数分布提示，由 NPC 决定开局。
3. 降低操作反馈延迟，并控制多人同时移动、集中加入、弱网重连时的服务器计算量、带宽和消息积压。

默认将“自定义人数”理解为**整个房间允许的同时在线玩家数**，四个阵营数量保持不变，不增加每队强制名额。优先优化当前单房间活动场景；多房间扩容作为后续路线。

服务器配置、部署地域、出口带宽和实际峰值人数尚未提供。下文的人数档位与性能指标是实施和压测目标，不代表已验证的承载能力。

## 2. 当前实现与瓶颈

| 位置 | 当前行为 | 改造原因 |
| --- | --- | --- |
| `server/index.ts` | `PLAYER_LIMIT = 50`，满员错误文案也固定为 50 | 无法自定义容量 |
| `server/index.ts`、`UIOverlay.tsx` | 服务端拒绝不均衡开局，前端同时禁用按钮 | 需要同时取消两处限制 |
| `GameCanvas.tsx` | 每 115ms 读取按键并发送移动 | 第一次按键可能等待接近 115ms 才发出 |
| `server/index.ts` | 活跃状态最多按 12Hz 广播全量玩家和箱子；空闲约每秒同步 | 动作执行后可能再等待约 83ms，且更新成本随人数、实体数增长 |
| `server/index.ts` | `boxAt()`、`playerAt()` 每次创建数组并遍历 | 连续移动、连推箱子和随机生成时重复计算、产生垃圾回收压力 |
| `server/index.ts` | 加入、恢复连接、离开会立即触发全量广播 | 集中进入时产生大量重复广播，接近二次方的扇出成本 |
| `server/index.ts` | 已有脏状态标记、广播共用一次序列化、512KB 背压跳帧 | 保留这些优化，但还需处理历史积压及后续增量同步的恢复 |
| `server/index.ts` | 移动在消息回调直接执行，没有服务端步频约束 | 消息越多移动越快，突发请求会抢占事件循环 |
| `server/index.ts` | 恢复连接不校验人数上限，离线玩家长期保留 | 可绕过容量限制，长期运行可能累积无用状态 |
| `server/index.ts` | 同阵营出生在同一格；随机空位查找失败直接返回地图中心 | 放大人数后会出现重叠，需要先建立正确的占位规则 |
| `useGameStore.ts`、`GameCanvas.tsx` | 每个 STATE 整体替换状态，再对权威位置做插值 | 本人操作等待往返网络，HUD 重渲染和多层插值增加体感延迟 |
| `docs/DEPLOY.md`、Compose | 单进程内存状态，同端口提供前端与 WebSocket | 扩容不能简单复制容器后随机分流同一局玩家 |

README 中“30Hz 广播”的说明与实际 12Hz 不一致，实施时一并修正。

## 3. 人数配置与开局规则

### 3.1 配置模型

建议新增独立的房间配置，不把人数混进地图宽高配置：

```ts
interface RoomConfig {
  playerLimit: number;
}
```

| 配置项 | 建议值 / 行为 |
| --- | --- |
| 默认人数 | 200，可由后台设置为更小的人数 |
| 可选人数 | 任意整数，从 1 到服务器公布的 `maxPlayerLimit` |
| 当前开放上限 | 200（按用户要求开放）；总连接默认 300 |
| 部署侧上限 | `MAX_PLAYER_LIMIT`，限制后台可填写的最大值 |
| 初始值 | `DEFAULT_PLAYER_LIMIT`，启动时校验不超过部署上限 |
| 修改时机 | 等待中或比赛结束后；倒计时、比赛中锁定 |
| 生效方式 | 独立“保存房间设置”，成功后立即影响加入校验，无需开局或重置地图 |
| 保存失败 | 显示具体原因，保留服务器当前有效值 |
| 重启行为 | 第一版运行时修改保存在内存，重启恢复部署默认值；后台明确标注 |

部署变量必须通过 Compose 传入进程，仅修改 `.env` 不够。人数上限同时受实际地图空位约束，不能只验证数值范围。

### 3.2 边界规则

- 下调人数时，如果小于当前在线人数，拒绝保存，不踢现有玩家。
- 新玩家加入与离线玩家恢复连接均执行相同容量检查；同一在线身份替换旧连接不重复占名额。
- 第一版按在线人数计名额，断线后释放，不预留席位；房间满员时，离线玩家恢复会收到“房间已满，请稍后重试”。
- 离线身份建议保留 5 分钟后清理；过期需重新加入。关闭旧连接时不得把已经重连的新连接标记为离线。
- 观众与后台不计入玩家名额，但计入独立的总连接上限与带宽预算；未加入连接也需要超时或明确观众身份。
- 延续目前新玩家可中途加入的行为：等待、倒计时、比赛中均允许加入，满员或无出生空位时拒绝；结束后可加入等待下一局。只有等待中允许换队。
- 出生优先选择本阵营基地内空位，再向基地附近扩展，所有玩家和箱子必须独占格子。
- 地图生成、重置、缩图采用候选世界校验：不足以安放全部在线玩家和箱子时拒绝操作，保留原世界，不能退回到地图中心重叠生成。
- 离线玩家不占格子；恢复时原位置被占用则重新寻找合法出生点。地图版本变化后同样重新验证位置。

### 3.3 不均衡也可开局

新的服务端开局条件：有操作权限、至少 1 名在线已入队玩家、比赛不在倒计时或进行中、配置与地图可用。

- 删除前端按钮和服务端 `ADMIN_START` 对队伍均衡的强制依赖。
- 允许 `10 / 2 / 0 / 0`、`1 / 0 / 0 / 0` 等分布直接开局，不要求满员或四队齐全。
- 保留队伍人数与差值显示；文案改为“人数不均衡，可直接开始”，不增加二次确认。
- 保留 3 秒倒计时、原始得分规则和手动选队，不自动重新分配队伍、不自动调整分数。
- 防止重复点击或重复消息重新生成战场：开始请求按状态机校验并返回明确结果。
- 标题改为“多人实时 3D 推箱子阵营战”，在线人数显示为“当前在线 / 配置上限”。

## 4. 延迟优化：按完整链路处理

当前操作反馈耗时可近似拆为：

```text
首次输入采样等待（0～115ms）
  + 上行网络耗时
  + 服务端排队和计算
  + 等待下一次广播（0～约83ms）
  + 下行网络耗时
  + 客户端渲染与插值
```

这不是实际测量结果，也不是延迟保证。优化需要区分真实权威确认耗时与本地视觉响应，不能用动画顺滑掩盖服务端积压。

### 4.1 输入及时发送，服务器控制速度

1. 首次按键立即发送，不再等待 115ms 的采样定时器；长按维持约 115ms/步的现有节奏。
2. 键盘与屏幕方向键统一走输入管理器，过滤浏览器重复 keydown；失焦、切后台、断线时清空按键。
3. 输入携带 `matchId`、`inputSeq` 和方向；序号在连接会话内单调递增，旧局、重复、非法输入拒绝执行。
4. 服务端用单调时钟控制每个玩家最小步间隔。较早到达的连续输入进入短队列，不能靠突发补发获得额外移动次数。
5. 建议每玩家最多缓存 2 个待处理动作，超时约 250ms 的排队动作丢弃；过载时返回拒绝结果，绝不积压数秒后集中执行。
6. 输入到达且满足步频时可即时执行；待处理输入由约 20ms 的调度周期公平轮询，每玩家每轮最多执行一步。该值需用压测调整。
7. 服务端对已执行、碰撞失败、过期、限流的输入都给出可终结的确认；确认仅回发操作者，并限制发送频率。

两条约束必须同时成立：首步低等待，持续移动不突破服务端速度限制。对连推、拉箱和斜向移动保留当前规则，另行用回归用例保证一致。

### 4.2 本地预测与服务端校正

- 在序号、服务端限速、输入确认和重同步机制完成后，再启用本地预测。
- 第一版只预测明确为空地的本人位移；推箱、拉箱、得分、重生等共享状态等待服务端确认。
- 预测前同时检查前方与身后箱子，避免把会触发拉箱的动作误判为普通移动。
- 客户端保留有界的未确认输入列表；收到权威位置与已处理序号后，从权威位置重放尚未确认且仍有效的输入。
- 碰撞冲突以服务端为准，小偏差短时平滑纠正，大偏差、重置和重连直接对齐。
- 本人模型、标记、昵称和相机共用同一个显示位置，避免各自插值造成跟随拖尾。
- 高 RTT 时限制最大预测步数和预测时长，超出后等待确认；不能长距离猜测，也不倒退整个共享世界进行延迟补偿。
- 他人及箱子按服务器时间戳插值，可从 50～100ms 缓冲开始调参；本人无需承担这段远端插值等待。

预测降低本地等待感，不会缩短真实网络往返，也不会让得分提前生效。

### 4.3 网格索引替代遍历

建立以下索引：

```text
playersById / boxesById       实体权威数据
playerByCell / boxByCell      格子 → 占用实体
baseByCell                   格子 → 所属基地
walls                        保留现有集合查询
```

普通查位从 O(P + B) 遍历降为平均 O(1)，长度为 K 的箱链检查接近 O(K)。移动、连推、拉箱、得分重生、加入、离开、重连和重置必须统一维护索引。

一笔动作先验证目标，再原子更新涉及实体与索引，最后处理得分和重生。重生不能占据该动作仍需使用的格子。开发测试中检查“实体位置与索引一致、无非法重叠、无越界”。

箱子卡死检测从每次广播扫描改为约每秒一次；60 秒重生规则不变。高密度地图生成使用可用格集合或有限搜索并显式失败，避免大量随机重试阻塞事件循环。

### 4.4 同步频率与增量广播

保留一次构建、一次序列化、多连接复用的广播方式，先降低每次广播成本，再决定是否提高频率。

| 消息类别 | 建议策略 |
| --- | --- |
| 输入确认 | 执行后及时回操作者；有界合并，避免被消息洪泛放大 |
| 玩家和箱子变化 | 活跃广播先保持 12Hz，优化后对比 15Hz、20Hz，再选择默认值 |
| 加入、离开、成员名单变化 | 合并进入下一广播窗口，避免每人进入立即全员全量推送 |
| 比分、比赛状态 | 变化时发布，与实体版本保持一致 |
| 倒计时、剩余时间 | 同步 `startedAt`、`endsAt`、服务器时间，客户端本地计算并周期校准 |
| 地图与静态资料 | 初次连接、版本变化、需要重同步时发送 |
| 全量快照 | 初次连接、恢复连接、版本断层和周期检查点时发送；检查点可从 5 秒开始调参 |

新增实体增删改集合，只发送实际变化的位置和属性。姓名、颜色等元数据在创建或修改时发送；仍以 JSON 为第一版格式，二进制编码和压缩根据 CPU/带宽测量再决定。

协议至少包含：

```text
protocolVersion / matchId / mapVersion
revision / baseRevision / serverTime
players: upsert + remove
boxes: upsert + remove
scores / match / roomConfig: 变化时携带
inputAck: 已终结序号、执行结果、操作者权威位置
```

输入确认与广播状态须标明关联版本，不能让迟到的旧快照覆盖较新的本人权威位置。

WebSocket 在同一连接内可靠有序，但**主动跳过增量包**会造成版本断层。服务端记录每个客户端已发送基线；发生背压跳帧后标记为“需要快照”，恢复时先发最新全量快照，再继续增量。客户端发现 `baseRevision` 不匹配也主动请求重同步。

不能简单丢掉一个增量后继续发后续增量，更不能无限保存历史补发。初期版本不兼容时提示刷新页面，避免新旧协议混用。

## 5. 高并发与弱网治理

### 5.1 连接、队列与背压

- 设置 WebSocket 最大入站消息长度，建议从 4KB 起；按消息类型验证结构，非法方向、空对象、`null`、超长字段均安全拒绝。
- 每连接设置令牌桶：正常移动约 9 次/秒，接收限额可先取 20 条/秒及小突发额度；与实际移动步频限制分开。
- JOIN、恢复、配置修改和重同步请求设置更低的独立限额。限制已建立连接数、待认证连接数及建立连接速率；共享校园出口下避免仅按 IP 过严限流。
- 握手阶段校验总连接上限，连接洪峰时限制 INIT 全量快照的生成与下发速率，防止尚未加入玩家的连接也耗尽带宽。
- 背压阈值参考每连接消息速率与“允许积压多久”，不机械沿用固定 512KB；超过阈值跳过可替代的动态更新，恢复后发快照。
- 已进入 WebSocket/TCP 发送队列的数据不能直接撤回；持续积压超过约 3 秒时关闭慢连接，由客户端重连获取最新状态。确认消息、快照也必须受发送预算约束。
- 加入服务端 ping/pong 心跳，例如每 15 秒探测、连续约 30 秒无响应清理；客户端使用带随机抖动的指数退避重连，例如 0.5、1、2、4 秒递增至 15 秒。
- 重连后不补发断线期间的移动；恢复身份并拿到最新快照之后再接收操作。满员与身份过期分别提示，避免无止境密集重试。
- 离线身份、限流器、输入队列和渲染缓存都设置清理路径，验证长期运行内存不会持续增长。

### 5.2 管理与身份约束

当前任何 WebSocket 连接都能发送开始/重置消息，恢复身份也只依赖公开的 `playerId`。这会使高并发下的状态和容量约束失去可信边界。

实施时增加最小管理员鉴权，服务器验证配置、开始和重置权限；公开观众页面不自动拥有管理权限。恢复连接使用不可猜测、与玩家绑定的会话凭证，不把凭证放进广播。密钥不写入前端构建产物。

### 5.3 部署与横向扩容

第一阶段继续使用单房间、单权威进程，避免同一局出现多个不一致的状态源。

- 选择靠近主要参赛者的服务器；条件允许时对比现场局域网与现有云服务器的 RTT、抖动和稳定性。
- 静态资源可由 Nginx/CDN 提供；WebSocket 配置正确的 Upgrade 和超时，代理超时应大于心跳失活判定时间，检查容器 CPU 限流与文件描述符上限。
- 记录服务器 CPU、内存、可用出口带宽和部署拓扑；不能仅凭“几核几 G”承诺人数。
- 多个独立房间需要扩容时，以 roomId 路由到对应权威进程。Redis 可管理房间归属或跨进程通知，不放入每一步碰撞计算链路。
- 同一房间无法通过增加普通副本自动扩容；若单房间 200 人仍达不到指标，优先检查热点、考虑视野区域订阅，再评估更复杂架构。
- 区域订阅是后续措施：需同步视野外连推箱链等交互依赖；全地图观众使用独立低频预算，不能套用玩家局部视野。
- 第一版仍为内存比赛状态，重启会丢失比赛；恢复运行中比赛需要额外的持久化设计，不包含在本次基础改造中。

## 6. 前端渲染优化

已有实例化网格继续使用，重点减少不必要工作：

- Zustand 按实体和低频字段订阅，人数、比分、名单、倒计时不随每个位置包整体重渲染。
- 复用 `Vector3`、`Color` 等对象，避免每实体每帧反复分配。
- 实例颜色只在成员或颜色变化时更新；位置仍按动画需要更新，剔除无效实体缓存。
- 远距离玩家昵称按距离裁剪，观众端可使用更低的昵称密度；根据设备帧耗时调整阴影和像素比。
- 页面展示 RTT、连接状态和“正在重连”；管理端展示实际在线玩家、观众连接数、广播频率和积压连接数。

用真实浏览器测试渲染性能；仅用无界面的 WebSocket 压测无法证明手机或投屏电脑流畅。

## 7. 实施顺序与改动范围

| 阶段 | 工作内容 | 完成标准 |
| --- | --- | --- |
| P0：建立基线 | 增加耗时/带宽观测、可重复的客户端负载脚本，记录当前行为 | 得到当前 50 人正常操作与集中加入的基线报告 |
| P1：功能落地 | 人数保存与同步、自由开局、状态机、最小鉴权、容量和出生规则 | 人数可改，不均衡可开局，边界条件通过 |
| P2：服务端优化 | 网格索引、服务端步频、输入确认、公平短队列、批量广播、心跳限流、慢连接治理 | 高频输入不加速，连接洪峰不拖垮正常玩家 |
| P3：同步和体验 | 版本化增量、快照恢复、及时首步、本地预测校正、订阅和渲染优化 | 弱网能恢复一致，普通移动响应改善且不重复计分 |
| P4：压测与上线准备 | 50/100/200 人分档测试、代理验证、更新部署说明，选定上线人数 | 形成带环境和指标的容量结论，可按配置回退 |

## 8. 验证与验收

### 8.1 功能与一致性

- 人数输入：最小值、最大值、越界、小数、非数字、比当前在线少、比赛中修改、多个后台同时修改。
- 容量并发：只剩一个名额时多人同时加入/恢复，最终不超限；在线身份替换不多占位；观众不占玩家名额。
- 开局：0 人拒绝；1 人、空队、严重不均衡允许；重复开始不重置比赛；正常倒计时一致。
- 地图：多人出生不重叠；小地图大量箱子配置安全失败；缩图失败保留原状态；重连位置被占用时安全安置。
- 玩法：普通/斜向移动、墙体碰撞、连推、拉箱、同色得分、错色不加分、卡死重生均保持规则。
- 同时争抢同格/同箱时只产生合法结果，不重复计分；索引始终与实体一致。
- 协议：非法消息不中断进程，重复输入不执行两次，旧局输入失效，丢弃增量后能正确恢复快照。
- 预测：碰撞失败、拒绝输入、重置、断线重连后没有永久偏移，服务端确认前不产生权威得分。

### 8.2 压测矩阵

| 场景 | 建议负载 | 观察重点 |
| --- | --- | --- |
| 常规活动 | 50 玩家 + 5 观众，默认地图与 220 箱子 | 基线与改造后直接对比 |
| 扩展人数 | 100 / 200 玩家 + 20 观众 | CPU、带宽、排队、输入确认 P95/P99 |
| 高密度交互 | 小地图、较多箱子、热点区域同时推拉 | 碰撞、链推、重生及公平性 |
| 集中进入 | 目标人数在 5 秒内加入 | INIT、名单广播、容量竞态、成功率 |
| 重连洪峰 | 一半玩家同时断线后恢复 | 退避、会话替换、快照流量 |
| 弱网 | RTT 50/100/200/400ms，抖动 20～80ms，丢包 1%/3% | 确认尾延迟、预测纠正、TCP 队头阻塞 |
| 慢接收端 | 部分观众限制下载速率 | 缓冲上限、内存、正常玩家是否受影响 |
| 持续运行 | 目标人数运行至少 60 分钟，周期加入/离开 | 内存、离线状态清理、GC、性能退化 |
| 实际终端 | 现场手机与投屏电脑 | 帧率、首步显示、相机跟随 |

负载客户端需按真实约 9 次/秒生成操作，同时覆盖成功移动、失败碰撞和推箱，不能只模拟保持连接或一直撞墙。非法高频输入另设场景，不能混入正常人数基线。压测端与服务端尽量分机运行，网络故障通过代理或系统网络仿真施加。

### 8.3 初始验收目标

以下指标在确定测试机器和目标人数后验收，不视作当前性能承诺：

| 指标 | 初始目标 |
| --- | --- |
| 本地普通移动视觉响应 | 预测启用、渲染正常时 P95 ≤ 50ms |
| 服务端接收合法可执行输入至确认入发送队列 | P95 ≤ 30ms，P99 ≤ 60ms；单独报告受步频约束的排队输入 |
| 客户端发出至收到权威确认 | 常规负载下 P95 以对应 RTT 基线 + 50ms 为目标；另报告本地按键至确认全链路耗时 |
| 事件循环延迟 | 目标负载下 P95 ≤ 20ms，无持续恶化 |
| 广播带宽 | 相同录制动作负载下，目标较现有全量广播减少至少 50%；计入快照与确认流量 |
| 持续运行 | 无持续增长的输入/发送队列，无持续内存增长，无状态一致性错误 |
| 容量余量 | 通过目标人数压力测试后仍保留约 30% 的 CPU 与出口带宽余量 |

RTT 通过应用层 ping/pong、客户端单调时钟测量；服务端处理耗时用自身单调时钟测量。不要直接用未校准的客户端与服务器时间相减。时钟偏移估计只用于比赛倒计时和远端插值，报告网络抖动下的误差。

服务器出口流量可先按以下公式估算，再以真实字节数校准：

```text
每秒出口字节 ≈ 平均广播消息字节 × 广播频率 × 接收连接数
              + 单独输入确认 + 初始化/重同步快照 + 协议开销
```

例如，若实测平均消息为 20KB、12Hz、100 个接收端，仅广播约为 24MB/s，即 192Mbps；这只是示例，不是本项目实测包大小。大量观众同样会消耗出口带宽。

## 9. 发布与交付物

先交付可用的人数设置和自由开局，再逐阶段引入性能优化。每个阶段运行 `npm run typecheck`、`npm run build` 及相应的规则/协议测试；最终附上同环境前后对比压测报告。

上线配置采用实际验证通过的人数档位。若更高档位失败，记录瓶颈并保持较低上限；不能只提高配置值就宣称支持更多玩家。部署安排在比赛之间，保留上一镜像与配置；退回旧版本也会丢失当前内存比赛，不能把版本回退当作无损恢复。

最终交付应包含：可自定义的人数后台、不受均衡约束的开局流程、低延迟同步实现、可复现压测脚本、实际容量与延迟报告、更新后的使用和部署说明。


## 10. 本次落地与方案调整

- 已落地 P1～P3 的人数配置、自由开局、最小鉴权、会话凭证、出生与容量约束、网格索引、输入确认、服务端限速、有界队列、心跳、重连、背压快照恢复、稀疏增量、本地预测和渲染订阅优化。
- P0/P4 已完成同环境旧版流量观察、50/100/200 人本机短测和 100ms RTT 加抖动代理测试；生产服务器、60 分钟持续运行、真丢包、重连洪峰及终端帧率量化尚未验收。
- 实测发现固定 20ms 轮询处理玩家队列会产生累积等待，最终改用每玩家下一次合法执行时间调度；持续输入约 120ms 一次，留出 5ms 调度余量，服务端最短步间隔仍为 115ms。
- 每次输入的终结结果单独确认；连续终结序号随全量快照发送。普通增量依赖同连接有序确认，不再向所有人重复发送全员输入序号，以降低带宽；确认被背压跳过后强制快照恢复。
- 仍保留 12Hz 默认广播；人数默认值与部署硬上限已按用户要求开放到 200，总连接默认 300；增量协议可通过 `SYNC_MODE=full` 回退为全量模式。后台可设置 1～200 人；更高人数须另行修改部署变量。
