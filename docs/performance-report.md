# 人数与低延迟改造：本机验证报告

日期：2026-11-16（Asia/Shanghai）。数据来自实际执行，原始 JSON 保存在 [performance/](performance/)。

## 验证环境与口径

- Apple M4、10 核、16GB 内存，macOS arm64，Node.js v26.12.0。
- 服务端与模拟客户端运行在同一台机器，依次执行各档负载，没有公网链路；测量结果不能直接外推到云服务器。
- 新版采用 `npm run build` 生成的生产服务，默认 64 × 64 地图、220 个箱子、12Hz 增量广播，测试进程人数硬上限为 200、总连接上限为 300。
- 每档持续发送操作 20 秒，约每 120ms 一次，随后收包 350ms；带宽为这段总收包字节除以名义 20 秒，略高于含尾部时间的实际平均值。
- 机器人根据收到的状态选择可移动方向，包含斜向、碰撞和推拉；新版成功移动比例约 81%～91%，没有用单纯保持连接或持续撞墙代替活动负载。
- 观众列包含 1 个用于鉴权和采集指标的后台连接，因此请求 5/20 个普通观众时，表中为 6/21。
- 输入确认延迟使用客户端同一单调时钟计算，包含负载生成器本身的计算和排队；CPU 为服务端进程占单核比例的每秒采样 P95，RSS 为采样最大值。
- 出口统计为所有模拟接收端收到的应用消息字节，包括输入确认、动态广播、周期全量和运行指标，未计 WebSocket/TCP/TLS 开销；初始化阶段单独统计。
- 改造前来自提交 `22eb8b48baaa2195c6c4410972ee891fc5e9ebb3` 的服务端源码。新旧地图随机生成、出生规则和同步协议不同，输入采用同一类主动移动策略，因此是相同负载口径的观察对比，并非同一世界逐帧重放的严格基准。

## 结果

| 场景 | 观众/后台连接 | 全部加入耗时 | 输入确认 P95 | 广播及确认流量 | CPU P95（单核） | RSS 最大 | 协议错误 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 改造前 50 人 | 6 | 0.64s | 无确认协议 | 82.10Mbps | — | — | 0 |
| 改造后 50 人 | 6 | 0.54s | 6.66ms | 14.14Mbps | 4.58% | 36.2MB | 0 |
| 改造后 100 人 | 21 | 1.56s | 10.86ms | 53.04Mbps | 6.66% | 46.3MB | 0 |
| 改造后 200 人 | 21 | 4.06s | 19.86ms | 165.00Mbps | 7.70% | 54.8MB | 0 |
| 50 人，增加约 100ms RTT | 6 | 3.67s | 117.29ms | 13.85Mbps | 3.71% | 37.3MB | 0 |

50 人档的活动阶段流量较旧版减少约 **82.8%**，集中加入阶段收到的总字节减少约 **87.3%**。旧版没有输入确认协议，不能据此声称权威确认延迟降低了多少倍。

200 人档在约 4.1 秒内完成加入，33,000 次输入均收到确认。各新版负载的事件循环指标约为 11.4ms（每秒 P95 的 P95），未观察到输入持续排队。首轮发现的 20ms 周期调度累积等待问题已修正为按玩家下一次可执行时间调度。

弱网场景使用本机 TCP 转发代理，两个方向各增加约 50ms 延迟，并分别施加 ±10ms 抖动。它保持字节顺序，不模拟真实丢包、TCP 重传或带宽不足。确认 P95 约 117ms，与增加的网络往返量级一致；该值不是本地预测的视觉响应时间。

## 功能回归与浏览器验证

自动测试覆盖真实 WebSocket 的鉴权、人数校验、最后一个席位竞争、满员恢复、在线身份替换、禁止比赛中改人数、不均衡开始、重复开始、输入限速和非法消息。另有网格索引、候选地图失败保留原状态、200 个同队玩家出生、推拉箱与得分、10,000 次随机移动一致性、稀疏增量合并、有界预测、背压快照恢复判断及延迟代理字节顺序测试。

执行 `npm test`、`npm run typecheck` 和 `npm run build`。构建仍有现有前端体积较大的提示，未把该提示当作性能测试通过的证据。

实际浏览器验证了：后台保存 80 人，玩家页同步上限；单人、其余队伍为空可以开始；刷新自动恢复同一身份；键盘输入可用；最终玩家页未观察到控制台错误。

## 容量结论与未覆盖项

后续按用户要求，默认人数与后台硬上限已开放到 200，总连接默认 300；本报告的原始测量数据不变。本机 200 人短测通过，不能视为生产环境的性能承诺。尤其需要核对服务器**出口带宽**：此负载下 100 人约 53Mbps、200 人约 165Mbps，仅按 30% 余量估算分别需要约 76Mbps、236Mbps 可用出口，且还未包含传输协议开销与静态资源下载。

尚未完成实际部署服务器的压测、60 分钟持续运行、1%/3% 真丢包、多个 RTT 档位、连接恢复洪峰、真实慢读连接长期压力以及现场手机/投屏电脑的帧率量化。背压逻辑已有单元测试，不能等同于全部真实弱网场景通过。多房间、区域订阅及比赛持久化保持后续范围。

## 复现

```bash
npm ci
npm test
npm run build
npm run benchmark -- --seconds 20 --weak-network --output-dir /tmp/holo-benchmark
```

基准工具启动独立测试服务，使用随机临时管理密码和随机端口，结束后关闭服务，不操作已有活动房间。可使用 `--only-weak --weak-network` 单独运行延迟代理场景。CPU 架构、Node 版本、地图生成及机器上的其他进程会影响结果。

要复核旧版，可从上述提交导出 `server/index.ts` 到本仓库下的临时 `.ts` 文件，再传入 `--baseline <文件路径> --baseline-port <空闲端口>`；必须位于可解析本仓库依赖的位置，完成后删除临时文件。普通 `benchmark` 不依赖旧版文件。

独立负载命令支持更长时长；应在专用实例执行，因为会修改房间设置、重置并开始比赛：

```bash
ADMIN_TOKEN=your-test-password npm run loadtest -- --url ws://127.0.0.1:3001 --players 50 --spectators 5 --seconds 3600 --output /tmp/holo-soak.json
```

真实服务器升档前，按规划文档的矩阵补齐网络、持续运行和终端验证，再提高 `MAX_PLAYER_LIMIT` 与 `MAX_CONNECTIONS`。现有 JSON 是本次 20 秒短测的记录，没有声称完成一小时稳定性验收。
